# 战斗系统反推计划

## 目标与原则

目标是从当前终末地客户端恢复可验证的战斗运行时语义，并为 Endaxis 的模拟和合法性诊断
提供事实依据。它不是根据技能描述补公式，也不是把现有模拟器行为反向当作游戏实现。

遵循以下证据优先级：

1. 当前版本的配置数据与 IL2CPP 类型/原生代码；
2. 可重复的运行时日志、Hook 或游戏内数值实验；
3. 游戏 UI 文本和官方说明；
4. 社区结论与现有 Endaxis 实现，只作为待验证线索。

每个结论必须记录客户端版本、来源路径、类型/方法身份、样本和置信度。无法区分的分支保持
未知，不通过“看起来合理”的常量补齐。

## 已有输入

- 本地 VFS 与 `manifest.hgmmap` 索引，可按逻辑路径读取当前客户端资源；
- SkillData、BuffData 等 JsonData/MemoryPack 的类型和 schema 提取工具；
- 当前客户端的 IL2CPP dump、类型字段、方法 RVA 和原生二进制；
- `tools/disassemble_rva.py` 与 `tools/inspect_process_rva.py`；
- AKEDB 整理数据，可用于发现对象关系和人类可读描述，但不能替代原始证据；
- Endaxis 现有配置、模拟日志和游戏内面板/排轴样本，可用于交叉验证。

开始分析前需为这些输入生成版本清单和哈希，避免把不同客户端版本的数据拼接为一条调用链。

## 领域拆分

| 领域 | 首批问题 |
| --- | --- |
| 技能生命周期 | 技能实例如何创建、检查、开始、分段执行、命中、结束和被打断 |
| 释放条件 | SP、终结技能量、冷却、状态、形态、层数、连携窗口如何共同决定可释放性 |
| 资源账本 | 资源在请求、开始、命中或结束哪个时点扣除/恢复，失败是否回滚 |
| Hit 与伤害 | Hit 如何选择目标，倍率、攻击、防御、抗性、暴击和增伤如何分层 |
| Buff/状态 | 添加、刷新、叠层、覆盖、周期触发、移除和来源归属 |
| 元素与异常 | 附着、燃烧、腐蚀等状态的积累、触发和持续逻辑 |
| 失衡与处决 | 失衡值、韧性、倒地窗口、处决资格和恢复 |
| 时间与调度 | 帧、逻辑 Tick、动画事件、延迟任务和同帧顺序 |
| AI 与主控 | 主控动作、非主控 AI、连携排队和队伍共享状态的边界 |

## 分阶段执行

### 阶段 0：固定证据集

- 记录游戏可执行文件、metadata、资源 manifest、TableCfg/JsonData 和 AKEDB 版本；
- 生成类型名、方法名、RVA、字段 offset 和配置表路径的可查询索引；
- 标记无法确认版本一致性的旧 dump，不让它参与最终结论。

产物：`combat-evidence-manifest.json` 及生成脚本。

### 阶段 1：建立类型地图

从 SkillData、BuffData 的 MemoryPack wrapper 反向展开运行时类型，优先收集：

- 稳定类型名、字段、继承和接口；
- formatter 字段顺序与配置 schema；
- 构造、反序列化、注册和查询入口；
- delegate、事件和条件类型；
- 与角色、技能段、Hit、Buff、属性和资源的引用关系。

产物：机器可读类型图和一份人工注释的领域词典。

### 阶段 2：配置到运行时对象

选择少量机制简单且已有游戏样本的技能，从配置 ID 开始跟踪：

1. 配置如何被加载和注册；
2. 运行时技能实例保存哪些配置引用和可变状态；
3. 技能段、Hit、effect、condition 和 trigger 如何实例化；
4. 同一个配置对象如何关联 UI 描述、动画事件和战斗执行。

优先使用一个普通战技、一个终结技、一个连携技和一个持续 Buff，暂不追求全干员覆盖。

### 阶段 3：恢复首条完整调用链

第一条链路聚焦释放合法性与资源：

```text
输入/AI 请求
  -> 技能候选选择
  -> 条件检查
  -> 冷却与窗口检查
  -> SP/终结技能量检查
  -> 技能开始
  -> 实际扣费与冷却写入
  -> 分段事件
  -> 技能结束或取消
```

对每个节点记录调用者、被调用者、关键字段读写和失败返回值。重点确认“检查时刻”和“实际
扣费时刻”是否一致，以及失败、取消和打断时是否回滚。

### 阶段 4：伤害与状态管线

从 Hit 应用入口分别向上追来源、向下追结果：

- 攻击方/目标属性快照时机；
- 基础值、倍率、加算区、乘算区和最终修正；
- 伤害类型、元素、暴击、防御和抗性；
- Buff 对属性与事件的监听顺序；
- 失衡、附着、异常和死亡的派生事件；
- 同一次 Hit 的数值与状态效果执行顺序。

公式必须用至少两个配置样本和一个运行时或游戏内数值样本交叉验证。

### 阶段 5：最小运行时探针

只有静态分析出现以下情况时才进入 Hook：

- 虚调用或泛型实例无法唯一定位；
- 配置字段经过运行时派生或缓存；
- 同帧事件顺序无法从反编译控制流确认；
- 需要核对实际分支、参数或返回值。

探针应围绕已知方法记录最小结构化数据，不做全局日志洪泛。每个 Hook 都要有版本、RVA、
线程、调用频率和移除方式说明。

### 阶段 6：战斗语义 IR 与 Endaxis 适配

确认后的规则先进入与 UI 和本地化无关的语义 IR：

- 稳定对象身份；
- 条件表达式；
- 资源读写；
- 状态转移；
- 定时与事件顺序；
- 数值公式节点；
- 来源和置信度。

Endaxis 通过适配器消费 IR。尚未确认的规则不得伪装成确定字段；模拟器专用近似需要明确
标注，不回写为游戏事实。

## 首轮任务

1. 为当前 IL2CPP dump 和资源建立证据清单；
2. 从 SkillData/BuffData schema 选出核心类型并生成引用图；
3. 找到技能释放请求、条件检查、资源扣除和技能开始的候选方法；
4. 选一个简单战技建立首条配置到调用链；
5. 用 Endaxis 现有技力日志和游戏内样本验证扣费时点；
6. 将结论、未知项和可复现命令写入独立案例文档。

## 明确暂缓

- 在事实层稳定前重启自动排轴算法；
- 一次性反编译全部游戏方法；
- 根据中文技能描述自动生成完整执行逻辑；
- 为追求“全覆盖”静默接受未知 MemoryPack 字段；
- 把 Shader、模型或音频支线工作混入战斗领域模块。
